1. Executive Summary

Goal

Extract the Modularity Engine from a single 3,512-line HTML file into a clean engine/content split where:

  • The engine (engine.html) contains all game logic, systems, and rendering code
  • Content files (JSON + SVG + audio) define everything the engine consumes: characters, weapons, enemies, stages, pickups, leveling, audio, mechanics, and visual assets
  • Any content pack can be loaded, swapped, or combined without touching engine code
  • The engine becomes a reusable "mod runtime" that any content creator can feed

3. Engine vs Content Classification

What Stays in the Engine

The engine contains all logic — things that process, calculate, render, and respond. It is data-agnostic: it reads configuration but never defines it.

SystemResponsibilityContent Dependency
EventBusPub/sub event routingNone (pure infrastructure)
GameStateState machine: loading→menu→playing→levelUp→gameOver→endScreenNone (fixed states)
GameLoopFixed-timestep 60fps update/render loopNone
CameraSmooth follow, screen shake, coordinate transformsNone
InputManagerWASD/mouse/touch/keyboard input, upgrade card selectionNone (reads canvas dimensions only)
EntityManagerObject pool, create/destroy/cleanup/getActiveNone (generic entity container)
SpawnSystemWave-based spawning, weighted selection, spawn rate controlReads: stages.waves, enemies[], stages.bossConfig
MovementSystemPlayer movement, enemy AI dispatch, projectile travel, boss state machineReads: enemy.behavior.pattern, mechanics.movement_patterns
CollisionSystemAABB collision detection, event emissionNone (reads entity sizes only)
WeaponSystemWeapon cooldowns, targeting, firing, level management, orb maintenanceReads: weapons[].statsPerLevel[], weapons[].type
DamageSystemApply damage with crits/iFrames, emit death eventsReads: entity stats (armor, critChance, critMultiplier)
PickupSystemEnemy death→drop rolls→pickup spawning, magnet attractionReads: pickups[], enemies[].drops
LevelingSystemXP tracking, level-up queue processingReads: leveling.xpCurve[]
RendererCanvas 2D drawing, entity rendering (with SVG cache), effects, UI overlayReads: ASSET_MAP, stage background config
FloatingTextSystemDamage/pickup floating textNone (text derived from events)
UIManagerLevel-up cards, end screen overlayReads: upgrade option data, end screen text config
AudioManagerWeb Audio synthesis, event→sound routing, pool management, duckingReads: audio_config.json, event-driven triggers
GameSystem orchestration, event wiring, upgrade option generationReads: all content data via DataManager

9. Audio & Graphics Pluggability

Audio Pluggability

The current AudioManager has 30+ hardcoded synth methods (_synthW1Fire, _synthZombieKill, etc.). The refactored version uses audio_config.json as a lookup table:

// AudioManager.play() — data-driven (replaces 30+ hardcoded methods)
play(soundId, options = {}) {
  const config = this.audioConfig.sounds[soundId];
  if (!config) return;

  if (config.type === 'synth') {
    this._playSynth(config, options);
  } else if (config.type === 'file') {
    this._playFile(config, options);
  }
}

_playSynth(config, options) {
  const sourceX = options.sourceX || 0;
  const sourceY = options.sourceY || 0;

  // Distance-based volume (existing logic, now generic)
  let volume = config.volume || 0.15;
  if (this.player && sourceX && sourceY) {
    const dx = sourceX - this.player.x;
    const dy = sourceY - this.player.y;
    const dist = Math.sqrt(dx * dx + dy * dy);
    const maxDist = 600;
    volume *= Math.max(0.2, 1 - dist / maxDist);
  }

  // Get a free slot from the pool
  const slot = this._getFreeSlot(config.priority || 1);
  if (!slot) return;

  const ctx = this.ctx;
  const osc = ctx.createOscillator();
  const gain = ctx.createGain();

  osc.type = config.waveform || 'sine';
  osc.frequency.value = config.frequency || 440;

  // Sweep
  if (config.sweep) {
    osc.frequency.setValueAtTime(config.sweep.start, ctx.currentTime);
    osc.frequency.linearRampToValueAtTime(config.sweep.end, ctx.currentTime + config.duration);
  }

  // Envelope
  const env = config.envelope || {};
  const t = ctx.currentTime;
  gain.gain.setValueAtTime(0, t);
  gain.gain.linearRampToValueAtTime(volume, t + (env.attack || 0.01));
  gain.gain.linearRampToValueAtTime(volume * (env.sustain || 0.5), t + (env.attack || 0.01) + (env.decay || 0.05));
  gain.gain.linearRampToValueAtTime(0, t + config.duration);

  osc.connect(gain);
  gain.connect(this.sfxGain);
  osc.start(t);
  osc.stop(t + config.duration + 0.05);

  slot.active = true;
  slot.startTime = t;
  slot.priority = config.priority || 1;
  slot.gainNode = gain;
}

// Renderer._drawEntity() — tiered visual rendering
_drawEntity(entity) {
  const ctx = this.ctx;
  ctx.save();

  // iFrame blink
  if (entity.iFrames > 0 && Math.floor(entity.iFrames * 10) % 2 === 0) {
    ctx.globalAlpha = 0.5;
  }

  const x = Math.round(entity.x);
  const y = Math.round(entity.y);
  const size = entity.size;
  const color = entity.visual?.color || '#FFF';
  const shape = entity.visual?.shape || 'square';

  // Tier 1: SVG asset
  const cacheKey = this._buildCacheKey(entity);
  const svgImage = this.imageCache?.[cacheKey];
  if (svgImage && svgImage.complete && svgImage.naturalWidth > 0) {
    const drawSize = size * 2;
    ctx.drawImage(svgImage, x - size, y - size, drawSize, drawSize);
  }
  // Tier 2: Shape primitive
  else if (shape !== 'none') {
    ctx.fillStyle = color;
    this._drawShape(ctx, x, y, size, shape);
  }
  // Tier 3: invisible (no else — nothing drawn)

  ctx.restore();
}

_buildCacheKey(entity) {
  // Build from content-provided data, not hardcoded type+shape+color
  const svgPath = entity.visual?.svg;
  if (svgPath) return svgPath; // Direct path as key
  return (entity.type || 'unknown') + '_' + (entity.visual?.shape || 'square') + '_' + (entity.visual?.color || '#FFF');
}

12. Gaps, Conflicts & Open Questions

Identified Gaps

Gap 1: No boss phase transitions implemented. The boss_gravekeeper.phases array defines two phases (HP thresholds, speed, charge intervals, minion spawning, ground pound), but the engine only uses the basic charge cycle. Phase 2's groundPound is defined but never triggered. Action: Phase 3 of migration should implement phase-dependent behavior reading from enemy.phases[].
Gap 2: Enemy projectile spawning for "caster" not implemented. The Caster enemy has behavior.params.projectileDamage and projectileSpeed, and the MovementSystem handles the "ranged" pattern (maintain distance), but there is no code to actually spawn enemy projectiles. Action: Need to add enemy projectile spawning in WeaponSystem or a new EnemyWeaponSystem, driven by mechanics.json ranged attack config.
Gap 3: Gold tracking not implemented. (RESOLVED) GameManager now tracks gold via addGold() / getResource(). PickupSystem writes gold on coin collection. Game._getStats() reads from GameManager. See 14_game_manager.md. Gold coins are spawned by PickupSystem but the LevelingSystem._onPickup() has a comment "Gold is tracked separately (not implemented yet)" and Game._getStats() always returns gold: 0. Action: Add gold state to Game or a new ResourceManager.
Gap 4: Upgrade options reference game variable instead of game parameter. In Game._showUpgradeOptions() (L3328), weapon upgrade lambdas reference game.weaponSystem and game.dataManager instead of the game parameter from the apply: (game) => {} callback. This is a latent bug — if game is in scope as a global (it is — const game = new Game() at L3365), it works accidentally. Action: Fix the lambdas to use the callback parameter consistently.
Gap 5: difficultyScaling formulas are strings, not executable. The stage data defines "hpMultiplier": "1 + 0.15 * minutes_after_boss_kill" as a string expression, but the engine never parses or applies these multipliers. Enemies spawn with their base stats. Action: Either implement a safe expression evaluator, or convert to numeric config with clear time breakpoints.
Gap 6: xpScaling.formula is a string, not executable. Same issue — "base_xp * (1 + 0.05 * floor(t / 60))" is defined but never applied. XP values come directly from enemy stats. Action: Same as Gap 5.
Gap 7: Boss announcement system not implemented. The bossConfig.announcement array defines timed text events (dim screen at 230s, text at 235s, boss spawn at 240s), but the engine only checks gameTime >= 240 for boss spawn. The "dim" and "text" announcement events are never rendered. Action: Implement a StageEventSystem that processes timed announcements.
Gap 8: No obstacle system. The stage data defines obstacle types and collision rules, but there's no ObstacleSystem in the engine. Action: Either implement obstacles or remove from stage data.
Gap 9: W3 area pulse visual uses setTimeout for pulse delay. In WeaponSystem._fireW3() (L1455-1460), setTimeout(() => { this.eventBus.emit('areaPulse', ...) }, i * 250) is used for multi-pulse delay. This is problematic because: (a) it fires outside the game loop, (b) it can fire after game over, (c) it doesn't respect pause state. Action: Replace with a queue-based delay system inside WeaponSystem.
Gap 10: No background music support. The AudioManager has no playMusic() or stopMusic() methods. The musicGain node is created but never used. Action: Add BGM playback methods during Phase 4 audio refactor.
Gap 11: Boss telegraph is hardcoded, not data-driven. The boss charge warning zone (Renderer._drawBossWarningZone() L1926-1975) and the charge state machine (MovementSystem._moveBoss() L1145-1205) are entirely hardcoded. Changing windup duration, charge speed, warning zone size, or adding new attack patterns requires editing engine JavaScript. External JSON cannot define new telegraph shapes or attack timings. Action: Implement a data-driven TelegraphSystem that reads attack definitions from enemy JSON. See 13_telegraph_and_boss_intro.md.
Gap 12: No boss introduction sequence. When the Gravekeeper spawns at 4:00, gameplay continues uninterrupted. No dramatic pause, no name card, no visual introduction. The stage data defines bossConfig.announcement[] (L437-439) with timed text events, but these are never rendered. Action: Implement a boss intro system: pause game → show overlay (boss image + name + subtitle) → resume. Also implement the announcement system for pre-boss tension text. See 13_telegraph_and_boss_intro.md.
Gap 13: No stage environmental hazard telegraphs. Stages cannot define environmental events (falling debris, lava pools, trap activations) that telegraph before dealing damage. The mechanics.json spec mentions stage events but there is no system to trigger, render, or resolve them. Action: The TelegraphSystem should support stage-triggered telegraphs with position randomization and persistent hazard zones after resolution. See 13_telegraph_and_boss_intro.md.

Identified Conflicts

Conflict 1: Weapon data indexed by array position vs ID. WeaponSystem._fireW1() reads this.dataManager.weapons[0], _fireW2() reads weapons[1], _fireW3() reads weapons[2]. This breaks if the weapons.json array order changes. Resolution: Change to weapons.find(w => w.id === 'w1_projectile') — read by ID, not position.
Conflict 2: PickupSystem creates pickups with hardcoded visuals, ignoring pickup JSON. In _onEnemyDeath() (L1601-1620), XP gem and gold coin visuals are hardcoded instead of reading from dataManager.pickups. The pickup JSON visual fields are defined but never used for these drops. Resolution: During Phase 2, read visuals from dataManager.pickups by ID.
Conflict 3: EventBus "death" event has inconsistent data. The CollisionSystem emits 'death' with data.entity and data.position, but the AudioManager's death handler reads data.type (which is data.entity.type). The pickup handler reads data.pickup.pickupData. The Game handler checks data.entity === this.player. This works but is fragile. Resolution: Normalize the death event data shape during Phase 2.
Conflict 4: Game time limit vs stage gameConfig. The 300s limit is hardcoded at L3188, but the stage data has bossConfig.spawnTime: "4:00" (240s). If someone sets a different time limit in gameConfig, the boss might spawn after the game ends. Resolution: Read both from stages.gameConfig and validate that bossSpawnTime < timeLimit.

Open Questions

Q1: Should the engine support multiple stages in one session? Currently the game has one stage. Should engine.html support a stage select screen and multiple sequential stages (like Vampire Survivors' stage progression)?
Q2: Should enemy projectiles be a new entity type? The "caster" enemy needs to fire projectiles. Should these be enemyProjectile entities with their own visual/behavior config, or should they be a subtype of the existing projectile type with a team flag?
Q3: How should boss phases be data-driven? The phases array in boss data has HP thresholds and stat changes, but transitioning between phases requires engine logic. Should the engine have a generic "phase transition" system that applies stat modifications when HP crosses thresholds?
Q4: Should audio support external audio files (MP3/OGG) or stay synthesizer-only? The audio_config.json spec includes a "type": "file" option, but the current AudioManager is purely Web Audio API synthesis. Should we add AudioBuffer loading for real audio files, or keep everything synthesized?
Q5: Should the content pack system be implemented now or deferred? The directory structure includes content_packs/ for alternate content sets, but implementing deep-merge override logic adds complexity. Should this be Phase 6 or deferred to a future version?
Q6: How should difficulty scaling formulas be handled? The current formulas are string expressions ("1 + 0.15 * minutes_after_boss_kill"). Options: (a) implement a safe math expression evaluator, (b) convert to structured config with numeric breakpoints, (c) keep formulas as strings and add a simple evaluator. Which approach?
Q7: Should the loading screen read its config from ui_config.json? Currently the loading screen HTML is hardcoded with "MODULARITY ENGINE" title. Since ui_config.json is loaded during the loading screen itself, there's a chicken-and-egg problem. Options: (a) hardcode the loading screen and accept it won't change with content packs, (b) use a minimal inline config for the loading screen only, (c) load ui_config.json with a separate small fetch before the main load.
Q8: Should weapon behavior (projectile firing, orbit maintenance, area pulses) be generically data-driven? Currently each weapon type has a dedicated method (_fireW1, _fireW2, _fireW3). Making this fully generic would mean defining "weapon behavior scripts" in JSON, which is very powerful but significantly increases engine complexity. How far should data-driven weapon behavior go?
Q9: What happens to the content/ directory when deployed via Freebuff's preview? The Freebuff platform serves from public/. The engine HTML and content files need to be at the correct relative paths. Should engine.html go in public/ and content in public/content/? Or should everything stay at root level?
Q10: Should the pickups.json dropConfig stay in pickups.json or move to enemies.json? Currently drop tables are defined per-enemy in enemies.json → drops.powerUpTable, but also referenced in pickups.json → dropConfig.sources. This is redundant — the same data exists in two places.
